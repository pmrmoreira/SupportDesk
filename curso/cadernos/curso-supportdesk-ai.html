3. Explicação dos conceitos

3.1. C#, .NET e ASP.NET Core

Já sabes usar C# para expressar instruções. A linguagem, por si só, não fornece tudo o que é necessário para compilar, executar, ler ficheiros ou receber pedidos web.

.NET é a plataforma que fornece ferramentas, bibliotecas e um ambiente de execução. O runtime é a parte que executa aplicações .NET. O SDK, ou kit de desenvolvimento, inclui as ferramentas para construir aplicações, além do necessário para as executar.

ASP.NET Core fornece as funcionalidades de desenvolvimento web em .NET. Por exemplo, consegue receber um pedido HTTP, escolher a função que deve tratar esse pedido e devolver uma resposta.

Termo Pergunta a que responde neste projeto
C# Em que linguagem escrevo a lógica?
.NET Que plataforma compila e executa o código?
SDK Que ferramentas uso para criar e construir a aplicação?
ASP.NET Core O que me permite receber pedidos web e responder?

Ponto de verificação P1: explica a diferença entre C# e ASP.NET Core usando o exemplo de um pedido de suporte.

3.2. Um programa de consola e um servidor web

Um programa de consola simples pode executar uma sequência e terminar. Um servidor web mantém-se em execução à espera de pedidos. Nesta aula, o processo .NET no teu computador desempenha esse papel.

O cliente é quem faz o pedido. Aqui será o navegador; mais tarde pode ser outra aplicação. O servidor recebe o pedido, executa código e envia uma resposta. Cliente e servidor são papéis, não obrigatoriamente dois computadores diferentes.

Navegador                       Aplicação ASP.NET Core
   |                                      |
   |  pedido: GET /api/health              |
   |------------------------------------->|
   |                                      | escolhe a função
   |                                      | executa C#
   |  resposta: estado 200 + dados JSON    |
   |<-------------------------------------|
   |                                      |
mostra o resultado                continua à espera de pedidos

O código C# deste exemplo executa no servidor. O navegador recebe o resultado; não precisa de executar esse C#.

3.3. HTTP, URL e porta

HTTP é o protocolo: as regras usadas para trocar pedidos e respostas web. Um pedido indica, entre outras coisas, um método, como GET, e um caminho. Nesta aula, GET significa que queremos consultar uma representação, sem pedir uma alteração aos dados.

Uma URL é um endereço. Observa este exemplo fictício:

http://localhost:5130/api/health
|      |         |    |
|      |         |    +-- caminho dentro da aplicação
|      |         +------- porta
|      +----------------- computador de destino
+------------------------ protocolo

localhost refere-se ao próprio computador. A porta permite distinguir serviços que estão a escutar nesse computador. Dois programas não podem, em geral, escutar simultaneamente no mesmo endereço e porta.

O número 5130 é apenas ilustrativo. A tua porta será mostrada no terminal. O WebLab e o SupportDesk.Web podem receber portas diferentes: anota o endereço de cada um.

HTTPS é HTTP protegido por encriptação durante o transporte. Para reduzir a configuração inicial, vamos criar esta aplicação de aprendizagem com HTTP local. Não enviaremos palavras-passe nem dados reais. Na aula 10 configuraremos HTTPS antes de trabalhar com login.

3.4. Endpoint e rota

Um endpoint é uma operação acessível por um método e um endereço. GET /api/health é um endpoint. Uma rota é a regra que associa um caminho a uma operação.

Nesta aula vamos usar um método chamado MapGet. Ele regista uma associação: «quando chegar um GET para este caminho, executa esta função».

O caminho /api/health é uma escolha nossa. A palavra api não ativa funcionalidades especiais. API significa interface de programação de aplicações: um conjunto de operações que outros programas podem usar. Esta é a nossa primeira operação.

3.5. Texto, HTML e JSON

O corpo de uma resposta pode transportar formatos diferentes.

  • Texto simples: uma frase, como Olá, Pedro!.
  • HTML: marcação que descreve elementos de uma página, como títulos e parágrafos. <h1>SupportDesk AI</h1> representa um título principal.
  • JSON: um formato textual para representar dados com campos e valores, como {"status":"ok"}.

Um objeto C# e o texto JSON que o representa são coisas distintas. Serializar significa transformar dados num formato que possa ser transmitido ou guardado. ASP.NET Core serializa automaticamente o objeto simples que vamos devolver.

O cabeçalho Content-Type indica o formato: text/plain, text/html ou application/json, por exemplo. Um cabeçalho é informação sobre o pedido ou a resposta, separada do respetivo corpo.

Um código de estado HTTP indica o resultado do pedido. Hoje precisamos de dois: 200, sucesso; 404, caminho/recurso não encontrado. Vamos aprofundar os restantes na aula 2.

3.6. O C# que vais encontrar

Este código representa uma função sem parâmetros que devolve uma string:

() => "Olá, Pedro!"

É uma expressão lambda, uma forma curta de escrever uma função. () indica ausência de parâmetros e a expressão depois de => fornece o valor devolvido. Para a mesma finalidade, poderíamos escrever um método:

string CriarSaudacao()
{
    return "Olá, Pedro!";
}

Nesta aula usamos a lambda porque a operação é pequena. A lógica de pedidos de suporte será organizada em métodos e serviços quando crescer.

Este código cria um objeto anónimo, um objeto cujo tipo não declaramos explicitamente com uma classe nossa:

new { status = "ok", lesson = 1 }

status é uma string e lesson é um número. É uma simplificação útil para respostas pequenas e fixas. Usaremos classes com nomes para os pedidos e os dados da API nas aulas 2–3.

Poderás também ver instruções diretamente em Program.cs, sem uma classe Program e um Main escritos por ti. São instruções de nível superior: o compilador organiza o ponto de entrada. O programa continua a ter um início de execução.

8. Erros frequentes e como os investigar

Um método de diagnóstico que vamos reutilizar

  1. Identifica a fase: comando, compilação, arranque ou pedido HTTP. Uma falha antes de o servidor arrancar não é um erro do navegador.
  2. Lê a primeira mensagem de erro relevante, não apenas a última linha «Build failed».
  3. Procura o ficheiro, a linha e a descrição. Compara com a última alteração que fizeste.
  4. Faz uma alteração pequena e testa novamente. Evita mudar várias coisas ao mesmo tempo.
  5. Regista a causa com as tuas palavras; isso será mais útil do que decorar a correção.

Uma mensagem de compilação pode ter este formato ilustrativo:

Program.cs(12,18): error CS1002: ; expected

Program.cs é o ficheiro, 12 a linha, 18 a coluna e CS1002 o identificador do erro. ; expected significa que o compilador esperava um ponto e vírgula. A causa pode estar também na linha anterior, por exemplo uma expressão que ficou por terminar. Os números de linha dependem do teu ficheiro.

Pontos de verificação P1–P7

  • P1: C# permite escrever, por exemplo, a função que descreve um pedido. ASP.NET Core fornece a infraestrutura para chamar essa função em resposta a um pedido web e transmitir o resultado.
  • P2: sim, os dois processos podem executar no mesmo computador. Neste projeto, o servidor executa o C# e o navegador apresenta a resposta.
  • P3: /adeus não corresponde a uma rota registada e devolve 404. Depois de parar o processo, uma nova tentativa pode falhar ao estabelecer ligação, o que é diferente de receber uma resposta HTTP 404. A aparência de conteúdo antigo no navegador não prova que o servidor continua ativo.

Revisão da secção 9 — Ideias que devem aparecer nas respostas

  1. Linguagem, plataforma, ferramentas de desenvolvimento e funcionalidades web têm responsabilidades diferentes.
  2. O cliente envia um GET; a aplicação encontra a rota; a lambda executa no servidor; o objeto é serializado; a resposta volta ao cliente.
  3. A porta participa na escolha do serviço de destino. Trocar a porta pode apontar para outro processo ou para um local onde ninguém está à escuta.
  4. Uma string é enviada como texto simples neste exemplo; o objeto é serializado como JSON. Content-Type descreve esse formato para o cliente.

3. Explicação dos conceitos

3.1. O pedido e a resposta têm partes diferentes

Um pedido HTTP combina um método, um endereço e cabeçalhos; pode também ter um corpo. O método indica a intenção. Hoje usamos GET para consultar. POST, introduzido na próxima aula, permitirá submeter um novo pedido de suporte.

Uma resposta tem um código de estado, cabeçalhos e, quando aplicável, um corpo. O estado informa o resultado; Content-Type descreve o formato do corpo. Não confundas o estado HTTP 200 com uma propriedade do teu JSON chamada status.

Cliente                          Servidor SupportDesk.Web
GET /api/tickets/1   ---------->  encontra a rota e lê id = 1
                                 procura o pedido no array
200 + application/json <-------  transforma o objeto C# em JSON
Estado Significado nesta aula
200 OK A consulta foi tratada com sucesso.
404 Not Found A rota não corresponde ou o pedido procurado não existe.
405 Method Not Allowed O caminho existe, mas não aceita o método usado.
500 Internal Server Error O servidor encontrou uma falha ao tratar o pedido; é necessário ler o erro.

Uma ligação recusada ocorre antes de receberes uma resposta HTTP. Primeiro confirmas que o servidor está ativo no endereço certo; depois investigas as rotas.

Ponto de verificação P1: o endpoint da aula 1 responde com 200 e {"status":"ok"}. Se mudares apenas o texto ok para offline, o código HTTP muda automaticamente? Justifica.

3.2. Um objeto e uma coleção em JSON

Um pedido individual é representado por um objeto, delimitado por { }. Uma coleção usa [ ]. As propriedades têm nomes e valores; números e booleanos não levam aspas. Não vais montar JSON por concatenação de strings: devolves objetos C# e o framework faz a serialização.

{
  "id": 1,
  "title": "Não consigo entrar",
  "status": "Open"
}

Uma lista vazia continua a ser uma lista válida: []. Consultar uma lista sem elementos pode ter estado 200. Procurar um pedido específico que não existe terá 404 no contrato que vamos definir.

Contrato significa aqui a combinação de caminho, método, estados e formato dos dados que os clientes podem esperar. Manter esse contrato previsível facilita construir a interface e os testes mais tarde.

3.3. Controllers e actions

Um controller é uma classe que agrupa operações HTTP. Uma action é um método dessa classe exposto como operação. Em vez de acrescentar toda a API a Program.cs, criaremos TicketsController com métodos para consultar pedidos.

ControllerBase fornece métodos como Ok(...) e NotFound(). Os atributos, escritos entre [ ] acima de classes ou métodos, fornecem informação ao ASP.NET Core: [Route] define o caminho e [HttpGet] o método HTTP. [ApiController] ativa convenções próprias de APIs; veremos a validação automática na aula 3.

São necessárias duas ligações em Program.cs: AddControllers() prepara os serviços dos controllers; MapControllers() disponibiliza os endpoints descritos pelos atributos. Mantemos Razor Pages para a página inicial e MapGet para os pequenos endpoints anteriores.

3.4. Um identificador vindo do caminho

Em /api/tickets/2, o 2 identifica o pedido. Com [HttpGet("{id:int}")], o segmento é capturado com o nome id, apenas se puder ser interpretado como um inteiro. O framework fornece esse valor ao parâmetro int id da action.

Há duas decisões distintas: encontrar uma rota e encontrar os dados. /api/tickets/abc não corresponde à rota com :int; /api/tickets/999 corresponde, mas pode não existir nenhum pedido 999. Nesta aplicação, ambos dão 404, por razões diferentes. A restrição de rota não substitui a validação das regras do negócio.

3.5. Localizar um objeto com LINQ

LINQ é um conjunto de operações de consulta sobre dados em C#. Vais usar FirstOrDefault: percorre a coleção e devolve o primeiro elemento que satisfaz a condição. Para a nossa classe Ticket, devolve null se não encontrar nenhum.

var ticket = Tickets.FirstOrDefault(ticket => ticket.Id == id);

A lambda recebe cada ticket e compara o seu Id com o parâmetro id. Depois precisas de decidir o que responder caso o resultado seja null. O nome da variável é independente da posição no array: o ID 2 não significa obrigatoriamente «segundo elemento».

3.6. Guardar versões com Git

Um repositório Git guarda o histórico de versões. Tens os ficheiros de trabalho, uma seleção de alterações preparada para guardar (staging area) e os commits, que registam essas versões com uma mensagem. Guardar no editor altera um ficheiro; fazer commit regista uma versão no histórico.

Editar e guardar → rever diferenças → selecionar alterações → fazer commit

O ficheiro .gitignore indica ficheiros ainda não seguidos que não devem entrar no histórico, como resultados de compilação. Git e GitHub não são a mesma coisa: o primeiro funciona localmente; o segundo pode alojar repositórios remotos. Nesta aula fazemos apenas commits locais.

3. Explicação dos conceitos

3.1. O corpo de um POST

O método e o caminho escolhem a operação. O corpo do pedido transporta os dados para essa operação. Content-Type: application/json informa o servidor de que o corpo está em JSON.

POST http://localhost:5011/api/tickets
Content-Type: application/json

{
  "title": "Impressora da receção sem ligação",
  "description": "A impressão deixou de funcionar esta manhã."
}

A linha vazia separa os cabeçalhos do corpo. No navegador, escrever uma URL na barra de endereços faz um GET; isso não envia este POST. Vamos usar os ficheiros .http do Visual Studio ou PowerShell.

3.2. O cliente não decide todos os campos

Um DTO, de Data Transfer Object, é um tipo que descreve dados trocados numa operação. CreateTicketRequest vai descrever o que aceitamos ao criar: título e descrição. Ticket continua a representar o pedido existente, com ID e estado.

Campo Quem o fornece nesta operação?
title Cliente; o servidor valida.
description Cliente; é opcional nesta versão.
id Servidor; escolhe o próximo identificador.
status Servidor; fixa Open na criação.

Se aceitasses diretamente Ticket e guardasses todas as suas propriedades, poderias permitir ao cliente escolher valores que pertencem às regras da aplicação. O DTO torna explícita a entrada pretendida. Não substitui autenticação ou permissões, que virão mais tarde.

Na configuração usada, propriedades JSON desconhecidas são ignoradas. Enviar "status":"Resolved" não provoca necessariamente 400; simplesmente não atribui esse estado ao pedido criado. A action construirá um novo Ticket com Open.

3.3. Ler, validar e só depois alterar os dados

Desserializar é transformar JSON num objeto C#. [FromBody] explicita que o parâmetro vem do corpo. Depois são verificadas regras de validação associadas às propriedades. Com [ApiController], entradas inválidas podem originar 400 antes de entrar na action.

JSON → leitura para CreateTicketRequest → validação dos atributos
                                          |
                           inválido → 400, sem criar
                                          |
                               válido → action → Ticket → 201

Usaremos [Required] para exigir o título e [StringLength] para limitar o seu tamanho. São Data Annotations, atributos de validação. Não confundas [Required] com inicializar uma propriedade: string.Empty evita um valor inicial nulo, mas não torna um texto vazio válido.

O corpo de erro terá normalmente status, title e errors. É uma resposta de validação, não uma exceção que tenhas de mostrar ao utilizador como «servidor avariado». Mensagens para JSON malformado podem vir em inglês; interessa identificar o campo ou o problema indicado.

3.4. Normalizar não é o mesmo que validar

Trim() remove espaços no início e no fim. Vamos usá-lo para guardar um título limpo. Os atributos verificam primeiro o texto recebido. Por isso, " a " pode satisfazer um mínimo de cinco caracteres antes de Trim(), mas ficar com apenas um depois.

Vamos verificar novamente esse mínimo na action, após normalizar, antes de inserir. O limite máximo dos atributos é aplicado ao texto recebido, incluindo espaços nas extremidades. Esta decisão fica explícita nos testes.

Ponto de verificação P1: se o título for inválido, deves atribuir um ID e acrescentar o pedido à coleção antes de devolver 400? Explica a ordem que escolherias.

3.5. A resposta de criação

201 Created comunica que criaste um recurso. Location é um cabeçalho que indica onde o cliente pode consultá-lo. CreatedAtAction constrói essa resposta com base numa action de consulta e nos valores da rota.

Vamos usar nameof(GetById) para obter o nome do método sem o escrever como texto solto. new { id = ticket.Id } fornece o valor para {id:int}. O terceiro argumento é o corpo da resposta.

GET continua a devolver 200 quando encontra um pedido. POST passa de 405, observado na aula 2, para 201 ou 400 conforme a entrada. Repetir um POST válido cria outro pedido nesta versão: ainda não existe um mecanismo para reconhecer repetições da mesma intenção.

3.6. Uma lista partilhada e pedidos simultâneos

Um array tem tamanho fixo; List<Ticket> permite acrescentar elementos com Add. A contagem da lista chama-se Count, enquanto o array tinha Length.

Vários pedidos HTTP podem executar ao mesmo tempo. Uma lista comum não deve ser lida enquanto outra operação a modifica sem coordenação. Usaremos um objeto partilhado TicketsLock e lock nas leituras e na criação. Só uma dessas regiões pode executar de cada vez para o mesmo objeto de sincronização.

O ID e a inserção ficam na mesma região protegida, evitando que duas criações escolham o mesmo ID. Na listagem copiamos os elementos para um array com ToArray() enquanto temos o lock; depois o framework pode serializar esse resultado sem percorrer a lista que está a crescer.

É uma solução curta para este laboratório, com leituras e criação num único processo e sem alterações aos objetos já criados. lock não guarda dados no disco nem coordena duas instâncias da aplicação. Na aula 4 vamos retirar estas responsabilidades do controller.

Revisão e pontos de verificação

  • GET consulta; POST solicita uma operação de criação neste contrato. Um 404 é uma resposta do servidor, não uma ligação recusada. Ticket representa um objeto; Ticket[] representa uma coleção. Guardar no editor não faz commit.
  • P1: validar antes de atribuir ID e inserir. Uma entrada rejeitada não deve alterar a coleção.
  • Exemplo guiado: o eco devolve {"recebida":"Teste enviado pelo cliente"} com 200. Não cria um pedido de suporte.
  • P2: mudou o valor no corpo do pedido e, consequentemente, a propriedade Text do objeto recebido; a lógica compilada permaneceu igual.
  • P3: coordenar só Add não impede duas chamadas de escolher o mesmo ID, nem protege uma leitura enquanto outra chamada altera a lista.
  • P4: nameof identifica a action, os valores preenchem a rota e o último argumento é o corpo da resposta. O GET em Location deve devolver o mesmo pedido.
  • P5: duas chamadas válidas criam dois objetos com IDs distintos. Um POST repetido não é automaticamente reconhecido como a mesma criação.
  • No depurador, um título vazio é rejeitado pela validação automática; " a " passa o comprimento da entrada e é rejeitado depois de Trim na action.

Exercício A — Pista e solução

Pista: altera a regra declarada no DTO e a mensagem que explica essa mesma regra.

[StringLength(80, MinimumLength = 5,
    ErrorMessage = "O título deve ter entre 5 e 80 caracteres.")]

Mantém [Required]. A verificação do mínimo após Trim continua a ser 5. Testa 80 e 81, porque um único caso «normal» não confirma o limite.

Exercício B — Pista e solução

Pista: combina a exigência de um valor com o intervalo na entrada e verifica o tamanho do texto normalizado antes de inserir.

Substitui os atributos da descrição no DTO por:

[Required(ErrorMessage = "A descrição é obrigatória.")]
[StringLength(2000, MinimumLength = 10,
    ErrorMessage = "A descrição deve ter entre 10 e 2000 caracteres.")]
public string? Description { get; set; }

Na action Create, depois da verificação do título e antes de Ticket ticket;, acrescenta:

        var description = request.Description?.Trim() ?? string.Empty;
        if (description.Length < 10)
        {
            ModelState.AddModelError(nameof(request.Description),
                "A descrição deve ter pelo menos 10 caracteres depois de remover espaços nas extremidades.");
            return ValidationProblem(ModelState);
        }

No inicializador do novo Ticket, substitui a atribuição da descrição por Description = description,. A regra é aplicada antes de modificar a coleção. Continuas a validar no servidor mesmo que uma futura página também impeça entradas vazias.

Exercício C — Pista e solução

Pista: são necessárias três peças: entrada validada, propriedade no modelo e atribuição na criação. Alterar apenas o DTO não guarda o valor.

Dentro de CreateTicketRequest, acrescenta:

[Range(1, 3, ErrorMessage = "A prioridade deve ser 1, 2 ou 3.")]
public int Priority { get; set; } = 2;

Dentro de Ticket, acrescenta:

public int Priority { get; set; } = 2;

No inicializador da action Create, acrescenta Priority = request.Priority,. O valor inicial 2 é usado quando a propriedade é omitida; valores explícitos 0 ou 4 são rejeitados pelo atributo. Os pedidos iniciais também terão 2 por predefinição.

Revisão final — Ideias essenciais

  1. O DTO descreve a entrada; o modelo inclui dados definidos pelo servidor. A criação liga os dois explicitamente.
  2. [ApiController] devolve erros de leitura/validação antes da action. As regras sobre o texto normalizado são verificadas depois.
  3. Inicializar evita um valor inicial nulo; validar verifica condições; normalizar transforma o texto.
  4. 201 comunica criação e Location permite consultar o resultado. Compara ID, título e estado no POST e no GET.
  5. A lista e o contador estáticos vivem no processo. O lock coordena acesso nesse processo. Nenhum dos dois oferece armazenamento persistente ou partilha entre processos.
